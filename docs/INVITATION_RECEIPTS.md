# Invitation receipts and failure stages

The sender observes Chrome performance events generated by its own visible UI
send. It never calls or replays LinkedIn's invitation API directly.

Network confirmation requires all of:

- A verified recipient profile URL/name and approved note, with one Send click.
- A fresh `Network.requestWillBeSent` event after this attempt was armed.
- HTTPS host `www.linkedin.com`, POST method and exact path
  `/voyager/api/voyagerRelationshipsDashMemberRelationships`.
- A response for the same request ID, host and path with HTTP status 200.
- No service-worker/disk-cache response or competing invitation request.

This is server acceptance of an invitation request, not the recipient accepting
the connection. The recipient binding is the verified UI profile and single send
operation; no claim is made that the private request body was inspected.

Network events are collected before DOM polling. A matching 200 can confirm even
when the click command or subsequent renderer read times out. HTTP 429 persists
a restriction and ends the batch, including when an earlier invitation in the
same batch was accepted. A visible Pending state remains a fallback, tied to the
same verified recipient. A closed modal alone never confirms a send.

`invitation_attempts` retains phase, whether a Send click was attempted, and
sanitized request/response metadata linked to the durable delivery reservation.
No headers, cookies, query strings, request bodies or message payloads are stored
in network metadata. The composer displays the stage and confirmation basis.

Failures at session/navigation/profile verification are blocked before any
invitation control is clicked. Failures after opening invitation controls without
conclusive acceptance remain uncertain. A Send click is never automatically retried. Legacy
uncertain deliveries without a network audit remain uncertain; unrelated current
HTTP 200 responses cannot retroactively reconcile them.

Profile headers support H1 and H2. Invitation dialogs inside LinkedIn’s interop shadow root are supported. The More-menu fallback uses only an observed
custom-invite link whose `vanityName` matches the verified profile. It never
constructs an invitation URL or clicks a recommended person's Connect control.

## Verification

`tests/test_invitation_receipt.py` exercises correlation, stale/cached/unrelated
200 rejection, metadata redaction, rate limits, click-timeout reconciliation and
failure-stage persistence. `scripts/invitation_network_smoke.py` uses a disposable
Selenium browser and a local HTTP stub to verify H1/direct, H2/More and shadow-dialog layouts,
exact note preservation and one simulated POST with no Pending UI.

Set `FIXTURE_SELENIUM_URL` to a dedicated test Selenium instance and `FIXTURE_HOST`
to this machine's address as seen by that instance. Never point this script at
the signed-in workbench browser. The fixture adapter rewrites local receipt URLs
for matching tests; it performs no real LinkedIn request.

## Explicit retries

An operator-authorized retry uses `POST /api/outreach` with one recipient,
`confirm: true`, the exact original `expected_notes`, and `retry_created`
matching the current receipt timestamp. Only blocked or uncertain receipts can
be retried; normal sends still reject any existing attempt. Stale retry requests
are rejected atomically. The sender checks the current recipient for Pending or
an existing connection before opening an invitation.

The previous delivery and its network audit are archived in
`outreach_attempt_history` before reserving the new attempt. Historical attempts
continue to count toward the UTC daily limit. Original receipts appear in the
composer, and holds, exclusions and replies still block retries. A new uncertain
result requires another explicit decision; it never triggers a send loop.
Profile elements replaced during identity checking are re-read before any action.
